# Product Sources

This Skill combines a small set of public product-management ideas. It does not reproduce any source as a complete method.

## Problem before solution

- [GOV.UK: Start by learning user needs](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs) treats user needs as the starting point for service work.
- [Intercom: Start with the problem](https://www.intercom.com/blog/intercom-product-principles-start-with-the-problem/) argues that teams should understand and prioritize the problem before choosing a solution.

Adaptation in this Skill: identify the material product decision before producing a PRD, task list, or implementation plan.

## Outcomes and product risk

- [Intercom: Deliver outcomes](https://www.intercom.com/blog/product-principles-deliver-outcomes/) distinguishes the intended change from the feature used to produce it.
- [SVPG: Four Big Risks](https://www.svpg.com/four-big-risks/) separates value, usability, feasibility, and business viability risks.

Adaptation in this Skill: state the user or business outcome, record observable acceptance, and surface only the risks that can change the release decision.

## Appetite and variable scope

- [Basecamp Shape Up: Set Boundaries](https://basecamp.com/shapeup/1.2-chapter-03) uses appetite to bound the investment before a team commits to a shaped project.
- [Intercom: Keep it simple](https://www.intercom.com/blog/intercom-product-principles-keep-it-simple/) favors the simplest solution that resolves the problem.

Adaptation in this Skill: Direct is the default. Planning depth grows only when the work has independently valuable outcomes, multiple writers, or a confirmed risk boundary.

## Product-manager responsibility

- [GOV.UK: Product manager](https://www.gov.uk/service-manual/the-team/product-manager) describes responsibility for product vision, strategy, priorities, and balancing user and business needs.
- [Atlassian: Product requirements template](https://www.atlassian.com/software/confluence/templates/product-requirements) provides a practical structure for goals, assumptions, user stories, design, and open questions.

Adaptation in this Skill: the product manager owns the product decision and acceptance boundary. Architecture ownership, implementation, and task-system administration remain separate roles.
